# Releases

Package: `@sd-softdev/opencode-codex-contingent` (public npm package).
Repository: `sd-softdev/opencode-codex-contingent`.

## Workflow

Only a pushed stable tag such as `v0.1.0` starts `.github/workflows/release.yml`.
The trigger's broad tag glob is followed by strict validation: prereleases,
malformed tags, leading-zero versions, and mismatches with `package.json` fail
before dependency installation or publication.

1. Check out the tagged commit with complete history and tags.
2. Validate the tag, install locked development dependencies without install
   scripts, type-check, run offline tests, build, and audit dependencies.
3. Compile Solid/OpenTUI TSX into `dist/tui.js`; UI runtime imports stay external.
4. Pack only compiled code, package metadata, license, README, security policy,
   and the fictional preview. Record the tarball's SHA-512 integrity.
5. Publish that exact tarball to the public npm registry using OIDC.
6. Query the exact published version, compare name/version/integrity, download
   its tarball, and independently hash it. A version not yet visible is retried
   up to 12 times, five seconds apart.
7. Generate notes from Conventional Commits and create the GitHub release,
   attaching the same tarball. This step cannot run after failed verification.

Releases are serialized. npm 11.16.0 is pinned for consistent packing and OIDC
support. There is no npm token in the workflow. The job runs only in the named
upstream repository, not forks. GitHub's short-lived token is exposed to the
release-creation step, not npm commands.

## One-time setup before pushing a release tag

1. Use the intended npm account (`npm whoami`) with publishing permission in
   the `sd-softdev` organization and interactive 2FA configured.
2. **Bootstrap the npm package if it does not exist.** npm's documented trusted
   publisher setup is in an existing package's settings. For a brand-new
   package, perform one explicitly approved, manual initial publication from
   the intended release commit after running the checks and build. Do not
   create a long-lived CI token to work around this prerequisite. The project
   does not automatically bootstrap a package or change npm account settings.
3. In the package's npm settings, add a GitHub Actions trusted publisher:
   - Organization/user: `sd-softdev`
   - Repository: `opencode-codex-contingent`
   - Workflow filename: `release.yml` (not its full path)
   - Environment: leave blank; this workflow does not name an environment
   - Explicitly allow **direct `npm publish`**; stage-only permission is not
     sufficient for this workflow.
4. Validate a new trusted publisher by running its first successful publication
   within npm's two-day configuration window. After a manual bootstrap at
   `0.1.0`, use the next real version, e.g. `0.1.1`, for this first OIDC publish.
   A rerun that only verifies an existing version does not validate OIDC access.
5. Prefer npm's **Require two-factor authentication and disallow tokens** setting
   after verifying OIDC. This does not block trusted publishing.

For the manual bootstrap, use the same pinned npm version and exact release
commit as CI. An already-published identical version can be verified by the
tag workflow and given a GitHub release without being published again.

Do not push a first release tag until the setup is ready. Tagging alone cannot
make missing npm permissions or a missing trusted publisher work.

## Create subsequent releases

Merge the intended changes to `main`, make sure the working tree is clean, and
increment the version locally. For example:

```sh
npm version patch -m "chore(release): %s"
git push origin main --follow-tags
```

`npm version` updates `package.json` and the lockfile, creates the version commit,
and creates the `vX.Y.Z` tag. The pushed tag must refer to that version commit.
Do not overwrite or move release tags. Major/minor version selection is a
maintainer decision; Conventional Commits do not automatically select it here.

## Release notes

The generator groups `feat`, `fix`, `perf`, `refactor`, `docs`, `build`, `ci`,
`test`, and `chore` commits. Unrecognized types and non-conventional messages
appear under **Other changes** rather than disappearing. Scopes are preserved.
Both `type!:` / `type(scope)!:` and `BREAKING CHANGE:` / `BREAKING-CHANGE:` body
footers create a **Breaking changes** section.

Notes cover the previous highest stable version tag reachable from the current
tag through the current tag. With no previous stable tag, all history reachable
from the tag is included. Tags from unrelated branches are excluded. Use
Conventional Commit titles when squash-merging pull requests.

These are commit-based notes generated by `scripts/release.mjs`, not GitHub's
PR-based `--generate-notes` feature.

## Failure and rerun behavior

- If checks, publication, or verification fail, no GitHub release is created.
- npm and GitHub are not a transaction: npm can succeed before GitHub fails.
  Rerun the same workflow. An existing version is accepted only if its name,
  version, and exact tarball integrity match the newly prepared artifact.
- A mismatched immutable npm version fails safely. Investigate the mismatch;
  do not delete versions or move tags to hide it. Use a new version for changes.
- An existing GitHub release is left unchanged; the workflow does not overwrite
  manually edited notes or assets.
- A network error can fail verification even after a successful publication.
  Check npm and rerun; do not assume a failed job means nothing was published.

Reference: [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).
